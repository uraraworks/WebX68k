# Web Serial

[English](WEB_SERIAL.md)

WebX68kでは、X68000のRS-232Cポート(Z8530 SCCチャネルA)を、Web Serial
APIでユーザーが選択したシリアルポートへ接続できます。

## 動作条件

- Web Serial APIに対応するブラウザ
  - デスクトップ版のChrome、Edge、Firefoxの現行リリース
  - Android版のChrome 148以降
- セキュアコンテキスト
- シリアル機器、または仮想シリアルポートのペア
- ブラウザのポート選択画面での明示的なユーザー許可

FirefoxがWeb Serialに対応したのはバージョン151からです。初回利用時には、サイトへ
Web Serial権限を付与するため、Firefoxが生成する合成サイト権限アドオンのインストール
確認がポート選択画面より先に表示されます。
企業ポリシーで管理されたFirefoxではWeb Serialが既定で無効になるため、管理者が
`DefaultSerialGuardSetting`を`3`に設定して許可する必要があります。

次の環境は現在対応していません。Android版Firefox、iOS/iPadOS上のすべてのブラウザ、
およびmacOS版Safari。APIを利用できないブラウザではシリアル操作欄を非表示にします。

## 接続方法

1. 「設定」を開きます。
2. ボーレートを選択します。
3. 「接続」を選択し、ブラウザの画面からシリアルポートを選びます。
4. 可能であれば、機器を取り外す前に「切断」を選択します。

通信形式はデータ8ビット、パリティなし、ストップビット1、ハードウェアフロー制御なし
です。ボーレートはブラウザストレージへ保存されます。ポートの許可と接続状態は
ブラウザが管理し、WebX68kは永続化しません。ポート選択をキャンセルした場合は
エラー表示にせず、未接続状態へ戻ります。接続先を毎回確認できるよう、接続操作の
たびにポート選択画面を表示します。

指定したボーレートはブラウザが物理ポートを開く設定であり、WebX68kの送信ペーシングにも使用します。送信FIFOは8N1の1文字を10ビットとして、最大約250ms分ずつブラウザへ渡します。`writer.write()` の完了がOSの送信キュー投入時点で返る場合でも、書き込み開始から算出した物理送信時間が経過するまでSCCのTX readyを戻しません。OSへの書き込み自体がそれより長い場合は追加で待たないため、同じ時間を二重に加算しません。

これはSCC内部の各ビットをCPUクロック単位で再現する実装ではなく、ブラウザへデータを渡す速度が選択した物理ポートの線速を超えないようにする送信側の近似です。受信タイミング、RTS/CTS、XON/XOFFはエミュレートしません。標準的な内蔵BRG/PCLK設定を検出できる場合は、X68000側の概算値とブラウザ側の選択値が一致しないと設定画面に警告します。外部クロックなど判定できない設定では警告しません。

## データフローとバックプレッシャー

ここでいうバックプレッシャーは、有限長FIFOとWeb Streamsの書き込み待機によって
生成側を一時停止するアプリケーション内部の容量管理です。RTS/CTSによる
ハードウェアフロー制御とXON/XOFFによるソフトウェアフロー制御は実装していません。

- ブラウザからの入力は4096バイト固定のSCCチャネルA受信FIFOへ入ります。
- FIFOが満杯の間は受信チャンクをJavaScript側で保持し、ゲストが読み出した次のフレームで再試行します。
- X68000からの出力は4096バイト固定のSCCチャネルA送信FIFOへ入ります。
- ブラウザへの書き込みは同時に1件だけ実行し、選択ボーレートの最大約250ms分に分割します。完了するまで次のデータをコアから取り出さないため、JavaScript側に無制限の待ち行列は作りません。
- 送信FIFOが満杯の間に加え、ブラウザの `writer.write()` と8N1の推定送信時間の両方が完了するまでRR0の送信可能ビットとRR1のAll Sentを解除します。
- 送信可能ビットを無視するゲストでは送信データが欠落する可能性があります。

受信割り込み、送信バッファ空き割り込み、RR8による受信、WR0の割り込みコマンドに
対応します。割り込み要因をラッチして公平に処理するため、連続したシリアル通信中でも
SCCチャネルBのマウス割り込みを妨げません。RR0のCTSとDCDはWeb Serial接続中だけ
ONとして返します。ブラウザ側のポートはハードウェアフロー制御なしで開きます。

## ステートセーブとリセット

名前付きステートはフィールド名で復元されるため、追加したチャネルAのフィールドが無い
ステートは、そのフィールドをリセット値として読み込みます。一方、従来コアが作成した
data_only形式の高速ステートとの互換性は保証しません。追加フィールドによってステート
全体のサイズが変わるうえ、旧レイアウトの読み込みを固定fixtureで検証していないためです。

ブラウザが管理する送受信FIFOの内容はステートへ保存しません。マシンリセット、
ステートロード、ブラウザからの切断、通信エラー時にFIFOを消去します。その境界で
通信中だったデータは失われる可能性があります。

## com0comを使ったWindowsでの実機スモーク(任意)

1. com0comをインストールし、例としてCOM10とCOM11の仮想ポートペアを作成します。
   COM10以降を一部のWindowsソフトで直接指定する場合は、Win32のデバイスパス形式
   (`\\.\COM10`、`\\.\COM11`)が必要なことがあります。Tera Termの一覧から
   選択する通常の操作では、COM10、COM11の表記のままで構いません。
2. WebX68kをペアの片側へ接続します。
3. Tera Termで反対側を開き、WebX68kと同じボーレート、8N1に設定します。
4. Human68k側で **CTTY AUX** を実行します。
5. Tera Termからコマンドを入力し、入出力が双方向に通ることを確認します。
6. Tera Termから **CTTY CON** を実行し、コンソール入力をX68000の画面と
   キーボードへ戻します。

Tera Termの送信・受信文字コードは、どちらも **Shift JIS** に設定してください。
別の文字コードでは日本語が文字化けします。

## 同梱コアのビルド

SCC実装はpx68k-libretro側の依存変更です。先にpx68k-libretro側でレビューと
マージを行い、そのコミットを指定してWebX68kの生成物を作成します。

~~~bash
EMSDK_DIR="$HOME/emsdk" \
CORE_SRC_DIR="../px68k-libretro" \
CORE_GIT_VERSION="<px68kのコミットID>" \
EMSDK_VERSION="6.0.7" \
./scripts/build-core.sh
~~~

EMSDK_DIR、CORE_SRC_DIR、OUT_DIR、CORE_GIT_DIR、CORE_GIT_VERSION、
EMSDK_VERSION、JOBS、CLEAN_BUILD、ALLOW_DIRTY、CORE_TEST_EXPORTSは環境変数で上書きできます。CORE_GIT_DIRは
WindowsのGit worktreeをWSLからビルドするときに使用できます。スクリプトは既定で
クリーンビルドを行い、コアのリビジョンを取得できない場合とEmscriptenのバージョンが
異なる場合に停止し、必要なC++リンカーモードを使用します。生成時のコアrevision、
dirty状態、Emscriptenバージョンは`px68k_libretro.build.json`へ匿名化して記録します。
通常ビルドではSCC診断用シムとJavaScript exportを含めません。実コア結合テスト用の一時ビルドだけ
`CORE_TEST_EXPORTS=1`を指定してください。manifestの`testExports`で通常生成物と
診断用生成物を区別できます。`CORE_TEST_EXPORTS=1`を`OUT_DIR`の明示なしで実行した場合は、
同梱用の`public/core`を上書きせずエラーで停止します。

## 自動テスト

`test/serial.test.ts`ではモックポートを使用し、対応ブラウザー判定、8N1での接続、
受信順序、受信容量に応じた待機、マシンリセット時の保持中受信データ破棄、
同時書込み1件の制限、リソース解放、読み書き失敗、read失敗時に送信中writerを
abortしてからポートを閉じる後始末、複数回および物理切断、接続キャンセル競合、
ポート選択キャンセル、接続失敗後の再試行、ボーレート保存、8N1送信時間、250ms単位の送信量、低速送信待ち中の切断をテストします。

`test/core-serial-integration.test.ts`では、コンパイル済みSCC実装のFIFO、割り込み、
要因消滅時のIRQ5取り下げ、切断、ステートロード、チャネルリセット時の共有WR2を
検証します。このテストにはSCC診断用exportを含むコアが必要で、同梱用の生成物では
実行できません。診断用コアはリポジトリ外の一時ディレクトリへ生成し、
ホストOSから見えるパスを明示してください。

~~~sh
CORE_TEST_EXPORTS=1 OUT_DIR=/path/to/temporary/core ./scripts/build-core.sh
WEBX68K_TEST_CORE_JS=/path/to/temporary/core/px68k_libretro.js npm run test:core
~~~

`WEBX68K_TEST_CORE_JS`が既存の診断用コアを指していない場合、`npm run test:core`は
黙ってスキップせず失敗します。

`npm test`は他のテストを実行し続ける必要があるため同じようには失敗させません。
代わりに、このファイルをスキップした実行では必ず標準出力へ
`[SKIP] test/core-serial-integration.test.ts`のブロックを出し、理由と上記2コマンドを
表示します。緑のサマリーだけを見て「実コア結合テストも通った」と誤解しないためです。

## 仕様メモ

- ブラウザ側とX68000側のボーレートは同じ値に設定してください。標準的な内蔵BRG/PCLK設定は不一致を警告しますが、外部クロックなど判定できない設定は利用者が確認する必要があります。
- 送信ペーシングはブラウザ側で選択した物理ポートのボーレートを基準にします。不一致警告が出ている場合でも自動的にポート設定は変更しません。
- `writer.write()` の完了は物理線上の送信完了を保証しないため、推定送信時間より早くTX readyを戻さない構成です。ハードウェアフロー制御は使用しないため、相手機器の受信能力を超える場合の損失までは防げません。
- 未接続中にX68000側から送信されたデータは破棄されます。SCCの送信準備状態は維持され、再接続後に古いデータが送信されることはありません。
- RR1はAll Sentを返します。ブラウザ入力はJavaScript側で保持して再試行するため、FIFO満杯だけではRx Overrunを立てません。
- OSまたはデバイスへの書き込み失敗後は、重複や順序逆転を避けるため、そのバイト列を自動再送しません。
- 割り込み要因が無くなった時点でIRQ5を取り下げます。受信FIFOを読み切った直後やマウスの最終バイトを読んだ直後に、要因のないpendingが残ることはありません。
- モデム制御は対象外のため、未接続中のCTSとDCDはLowのままです。
- ビルド設定は`EMSDK_DIR`、`CORE_SRC_DIR`、`OUT_DIR`、`CORE_GIT_DIR`、
  `CORE_GIT_VERSION`、`EMSDK_VERSION`、`JOBS`、`CLEAN_BUILD`、`ALLOW_DIRTY`、
  `CORE_TEST_EXPORTS`で変更できます。
- コアの作業ツリーがdirtyの場合、`scripts/build-core.sh`は既定で停止します。意図したローカル変更を使う場合だけ`ALLOW_DIRTY=1`を明示してください。

上記の挙動は「自動テスト」の節に挙げたテストで検証済みです。レビュアーが手動で
再実行する必要はありません。com0comの手順は、機器または仮想ポートペアを既に用意して
いる場合の任意の実機スモークです。

## 対応範囲

本機能はCTTY AUXや一般的な非同期8N1ターミナル通信を対象とします。同期モード、
パリティ・フレーミングエラー、BREAK、DMA/WAIT、外部ステータス割り込み、
インサービス管理（WR0のReset Highest IUSを含む）、モデム制御を前提とする通信ソフトは対象外です。
